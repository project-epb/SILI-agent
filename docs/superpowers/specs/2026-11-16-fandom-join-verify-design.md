# Fandom 群入群验证（官方 QQ bot）

## Goal

Fandom 编辑者 QQ 群要求申请人证明自己是某个 Fandom 用户。旧流程靠申请人的 QQ 号，官方 QQ bot 拿不到 QQ 号，所以 v5 上线前要换一套不依赖 QQ 号的验证。

## Scope

- In：wiki 侧 gadget 改写；v5 的入群申请自动验证插件；wiki 上管理员手动核对。
- Out：v4 的 `verify-fandom-user` 插件（v4 只搬不改，原样保留）；把验证结果同步到 Koishi 账号绑定。

## Decisions

1. **一次性随机码代替 QQ 号。** gadget 在浏览器里生成 16 位 Crockford base32 随机码（去掉 I、L、O、U），把 `时间戳#sha1(时间戳#随机码)` 写进 `User:<用户名>/qq-hash`，并显示入群答案 `<wgUserId>-<随机码>` 和复制按钮。生成框出现在验证页面和用户自己的 `qq-hash` 页上。
   Why：QQ 号只是把申请人对上 wiki 账号的钥匙，随机码同样能做到。只有本人能编辑自己的用户子页，所以"页面里的哈希能对上答案里的码"就证明了申请人持有本人生成的码。
   Rejected：8 位码——40 位强度，SHA-1 在 2 小时有效期内可被显卡穷举反推。

2. **答案里写 Fandom 用户 ID，不写用户名。**
   Why：QQ 入群答案最多 30 个字符。用户 ID 约 8 位数字，答案约 26 个字符；用户名可能更长。Fandom 用户 ID 全站统一，改名也不变，`list=users&ususerids=` 能查回用户名（已实测）。
   Rejected：答案只写随机码，再由 SILI 扫最近更改反查页面——可行，但有了用户 ID 就不需要了。
   Rejected：SILI 开 HTTP 接口签发短码——要对公网开接口、处理跨域和防刷，gadget 还可能受 Fandom 的内容安全策略限制。

3. **校验步骤。** SILI 从申请内容里匹配 `数字-16位码`（不区分大小写），按用户 ID 查出用户名，读该用户 `qq-hash` 页的最新版本，依次检查：最后编辑者是本人；时间戳在 2 小时内；`sha1(时间戳#随机码)` 与页面一致；该码没有用过。验证的 wiki 是 `community.fandom.com/zh`。

4. **通过就自动同意，失败不拒绝。**
   Why：失败可能是拉小号等正常情况，交给管理员判断。不自动拒绝，也就不需要受字数限制的拒绝理由。

5. **新表 `fandom_verify`**：页面里的哈希（主键）、wiki 用户 ID、wiki 用户名、平台、机器人 selfId、群 openid、申请人 openid、时间。只在验证通过后写入。
   Why：同一张表既判断"码已用过"，也记录"这个群成员是哪个 Fandom 用户"。

6. **每个申请在群里只发一条原生 Markdown 消息**。申请人尚未入群，不 @，用申请事件里的 QQ 昵称。出错时附带具体错误信息。
   - 通过：`✅ 已自动同意入群：<昵称>` / `Fandom 账号：<用户名>`，用户名链接到其用户页。
   - 待审核：`⚠️ 入群申请待人工审核：<昵称>` / `原因：<原因>`；已查到用户名时再附一行链接到他的 `qq-hash` 页，管理员点开就是核对框（决定 9）。

   Why：官方 bot 的纯文本消息不能带未备案的网址，Markdown 链接可以（MediaWiki 插件已在用）。

   | 情况 | 原因 |
   |---|---|
   | 答案里没有验证码 | 答案里没有验证码，可能没在 wiki 上做验证 |
   | 用户 ID 查不到 | 答案里的 Fandom 用户 ID 不存在 |
   | 验证页不存在 | Fandom 账号「<用户名>」还没生成验证码 |
   | 最后编辑者不是本人 | 「<用户名>」的验证页最后不是本人编辑的 |
   | 超过 2 小时 | 验证码已过期（有效期 2 小时） |
   | 哈希对不上 | 验证码和「<用户名>」的验证页对不上 |
   | 码已用过 | 这个验证码已经用过了 |
   | 查询 Fandom 出错 | 查询 Fandom 失败：<错误信息> |
   | 验证通过但同意失败 | 验证已通过，但自动同意失败：<错误信息>，请手动同意 |

7. **群消息用申请事件的事件 ID 做被动回复，不行再发主动消息。**
   Why：qq-crack 把 `join_request_id` 放进 `session.messageId`，直接 `session.send` 会把它当成被动回复的 `msg_id` 发出去。

8. **只处理配置里列出的群**，群 openid 由环境变量提供（Fandom 群，本地测试时加沙盒群）。插件装在 v5 的已服务上下文里，群需要先激活。

9. **wiki 上保留管理员手动核对，入口有两个**，都是 sysop 才能看到的"核对入群答案"框，粘贴 `用户ID-随机码` 后显示是否匹配、生成于多少分钟前，不经过 SILI：
   - 别人的 `User:<用户名>/qq-hash` 页面上：核对对象就是该页面的用户，答案里的用户 ID 与该用户不符时直接提示不匹配。
   - 放 gadget 的验证页面上：gadget 按答案里的用户 ID 查出用户名，再读他的验证页。

   Why：SILI 宕机时管理员仍能审核。管理员一般从最近更改点进别人的 `qq-hash` 页，不一定记得验证页面的名字，所以子页面上也要有核对框。手动核对无法判断码是否用过（记录在 SILI），SILI 宕机期间也不会消耗码，可以接受。

10. **gadget 仍用 ES3 写法**，源码放进本仓库，手动部署到 wiki。
    Why：Fandom 对 gadget 的语法要求；放进仓库方便和插件一起维护。

11. **新 gadget 在生产切到 v5 的同时部署。**
    Why：新 gadget 写的页面格式，v4 的旧插件认不出来；提前部署会让 v4 的自动验证全部失败。

## Acceptance

- 用新 gadget 生成答案后，在已激活的测试群申请入群，SILI 自动同意，群里出现通过消息，`fandom_verify` 多一行。
- 同一个答案再申请一次，不同意，群里提示"这个验证码已经用过了"。
- 答案为空、ID 不存在、页面不存在、他人编辑、过期、哈希不符时，各自出现对应原因，申请保持待处理。
- 未列入配置的群收到入群申请时，插件不响应。
- sysop 在别人的 `qq-hash` 页和验证页面上粘贴答案，都能看到匹配结果；粘贴错误答案、或在 A 的页面粘贴 B 的答案，显示不匹配。
- v4 的启动快照不变。
