# OneBot → 官方 QQ bot 数据迁移设计

把 `v4`（OneBot）上的用户身份和群设置迁到 `v5`（官方 QQ bot）。在 Koishi 里 OneBot 和官方 QQ bot 是两个不同的平台，大多数用户数据在 OneBot 这边。官方 bot 的 openid 按「机器人 × 人」区分（同一机器人下，同一个人在各群和私聊里的 openid 相同），无法由 QQ 号推出，`union_openid` 也不可用，所以由用户自己证明「OneBot 上的这个 QQ 号和官方 bot 上的这个身份是同一个人」。

## 目标 / 非目标

- 目标：用户自助把官方 bot 上的身份并入 OneBot 上的老账号；op 按群一次性迁移群设置。
- 非目标：批量自动迁移；迁移期间继续提供 OneBot 上的任何其他服务；跨机器人的统一身份（`union_openid`）。

## 迁移期运行形态

- 同一时间只运行 `v5` 一个进程。迁移期间 `v5` 额外加载 OneBot 适配器（以 `ONEBOT_SELFID` 是否设置为开关），**OneBot 只接收绑定码，其余一概不处理**：所有 OneBot 会话被访问控制的守卫视为未服务，不建用户、不建频道、不入库（见访问控制 spec「迁移期的 OneBot 会话」）。
- 依赖顺序：用户迁移要求普通用户能私聊官方 bot，即机器人已在后台公开；公开之前，访问控制 spec 里的守卫必须完成并验证。
- 迁移期结束后删除 `ONEBOT_SELFID`，OneBot 不再加载，不需要改代码。

## 用户迁移：使用 `@koishijs/plugin-bind`

用户迁移不另写代码，直接用 Koishi 的 `bind` 命令。它本来就是 SILI 跨平台（Discord、钉钉等）合并账号的工具，迁移只是其中一种用法。

流程：

1. 用户私聊官方 SILI 发 `bind`，得到绑定码（5 分钟有效，存在内存里，重启即失效）。
2. 用户用旧 QQ 号，在任意一个有旧 SILI 的群里把绑定码原样发出。OneBot 是真实 QQ 号，不加好友，没有私聊，只能在群里发。
3. 官方 bot 上的身份并入旧账号。

`bind` 的语义（`@koishijs/plugin-bind` 1.5.1）：

- 发起 `bind` 的账号，并入**发出绑定码**的账号所属的 Koishi 用户：把 `binding`（`platform = qq`，`pid = openid`）的 `aid` 改为旧用户 id，`bid` 保留发起方原来的用户 id。数据不合并，只是换了归属。
- 旧用户的 `id`、`authority`、LLM 记忆全部保留（记忆键是 Koishi `user.id`；记忆的平台名里 OneBot 映射为 `qq`，与官方适配器一致，并入后能直接接上）。
- 发起方原来的用户不再使用。它通常是空的：私聊守卫只在用户发 `bind` 时才为他建用户。迁移前已经在已激活的群里用过新机器人的用户，那部分数据会随之不再可达；在迁移公告里提醒「先迁移再使用」。
- 用户可以在官方 bot 上发 `bind -r` 撤销，身份退回到 `bid` 指向的原用户，旧账号不受影响。
- 一个旧账号可以被多个身份并入（共用同一份数据），不存在「迁移后锁定」。
- 改绑时如果这个 openid 有正在处理的会话，之后的写入可能落到旧用户上（Koishi 按写入时的 binding 落库），影响限于少量字段，接受。

`bind` 的最后一步用 minato 的 `set` 改写发起方的绑定行，而 `set` 只更新已有的行、不会新建。所以发起方必须已经有用户和绑定记录：私聊守卫对 `bind` 放行时，`autoAuthorize` 必须返回 1（见访问控制 spec）。否则插件会回复「绑定成功」，实际什么都没写。

文案：plugin-bind 自带的 zh-CN 文案（「原始平台 / 目标平台」）很难读，在 `v5` 里覆盖。Koishi 的 i18n 后定义的生效，所以覆盖必须在 plugin-bind 加载之后（它注入 `database`，覆盖的插件也要等 `database` 就绪并排在它后面）。文案要通用，因为 `bind` 也用于绑定 Discord、钉钉等平台。方向用「大号 / 小号」表达：发起 `bind` 的账号会被视为小号，发出绑定码的是大号，数据以大号为准，小号的发言都算大号的，小号原来的数据暂停使用、取消绑定后恢复：

```yaml
commands.bind:
  description: 把多个账号绑成同一个人
  options:
    remove: 取消绑定，恢复成独立账号
  messages:
    # 每个 <message> 单独发出：绑定码独占第二条，长按即可整条复制
    generated-1: |-
      <message>
      请在 5 分钟内，用你的大号（要保留数据的那个账号）把下一条消息里的绑定码发给 SILI。
      之后，当前账号会被视为你的小号：
      · 小号说的话，SILI 都当成大号说的
      · 小号原来的记忆、权限、称呼暂停使用，取消绑定后恢复
      想取消，在当前账号发「bind -r」。
      </message>
      <message>{0}</message>
    # 群里发起时，大号发出第一串码后看到
    generated-2: |-
      <message>
      还差一步：请在 5 分钟内，用刚才发起绑定的那个账号把下一条消息里的绑定码发给 SILI。
      完成后，那个账号会被视为你的小号，数据以当前账号为准。
      </message>
      <message>{0}</message>
    self-1: 要用你的大号发，不是当前这个账号。
    self-2: 要用刚才发起绑定的那个账号发，不是当前这个账号。
    # 两边都可能看到，只能写不区分大小号的话
    success: 绑定成功，两个账号现在算同一个人。
    remove-success: 已取消绑定，当前账号恢复成独立账号，原来的数据也回来了。
    remove-original: 这是大号本身，没有可以取消的绑定。
```

迁移的具体说法写进群提示和迁移公告，不写进命令文案。

### 入口：别名与私聊菜单

- **中文别名「多账号绑定」**（只在 `v5` 加）。不要用 `ctx.command('bind')` 去拿已存在的命令：在 Koishi 4.18.9 里它会把命令的调用者上下文改成调用方的插件，有副作用。用 `ctx.$commander.get('bind')` 取命令对象再 `.alias(...)`；plugin-bind 要等数据库就绪才注册命令，所以同时监听 `command-added`，在 `bind` 出现时加别名。
- **私聊菜单**（官方 `PUT /v2/menu`）：一个按钮「多账号绑定」，类型 `send_message`，内容「多账号绑定」。点击后文本被填进输入框，用户还要再点发送。菜单只在私聊出现、对所有用户相同，每次调用会覆盖整个菜单，所以菜单只由一处代码在 `v5` 启动时统一写入。迁移期结束后按钮保留，`bind` 以后用于绑定其他平台。
- 私聊守卫要同时认 `bind` 和「多账号绑定」（见访问控制 spec）。

### 群提示

群**首次被激活**、且处于迁移期（设置了 `ONEBOT_SELFID`）时，发一次迁移提示。激活的三条路径都算：群里 `@bot assign`、管理页面开关、群迁移命令。是否已发送记在 `qqbot_channel` 上，每个群只发一次；迁移期结束后不再发。

发送方式：`assign` 和群迁移命令本身是群里的一条消息，提示作为对它的被动回复发出，不需要主动消息权限。从管理页面激活时没有可回复的消息：`allow_proactive_msg` 为真就发主动消息，否则挂在这个群的下一条消息上被动回复。

```
全新 SILI 闪亮登场！旧号上的记忆、称呼和权限可以带过来：
1. 点我的头像，加我为好友
2. 在私聊里点输入框上方的「多账号绑定」，再点发送
3. 用你的旧 QQ 号（大号），把收到的绑定码发到有旧 SILI 的群里
⚠ 绑定码只能是你自己领的，别人给的不要发。
```

如果这个群是通过群迁移命令迁过来的（审计表里有对应的旧群号），旧 SILI 就在同一个群里，第 3 步写成「发到本群就行」。

### 旧号被 @ 时的提醒

迁移期内，有人在群里 @ OneBot 旧号（且不是在发绑定码）时，旧号回一条提醒：旧号不再回复消息，请群主或管理员把新 SILI 拉进群（附新号的拉群链接，即官方 `/users/@me` 的 `share_url`），以及如何用「多账号绑定」带走旧数据。每个群 8 小时最多一次，计时在内存里，重启后重新计。只做被动提醒，不做一次性群发：用真实 QQ 号群发是风控最严的行为。

### 风险

钓鱼：攻击者把自己领的绑定码诱骗别人在群里发出，攻击者的身份就并入了受害者的账号。命令文案防不住（文案只给领码的人看），所以群提示和迁移公告里都写明「绑定码只能是你自己领的，别人给的不要发」。受害者事后没法把攻击者踢出去，需要管理员处理。

## 群迁移

- 命令 `group-migrate <旧群号>`，别名「迁移群设置」。在官方 bot 所在的新群里 `@bot` 执行，要求 `authority ≥ 4`，参数是旧的真实 QQ 群号。op 在私聊完成用户迁移后，在群里是同一个身份。这条命令是群守卫的白名单命令，可以在未激活的群里执行。
- 两段式，不用 `session.prompt`（未激活的群里，非白名单消息会被守卫丢弃）：不带 `-y` 时只展示预览，包括新群名称（官方 `info` 接口）和旧群记录摘要；带 `-y` 才执行。
- 字段处理：
  - 复制：`switch` 的 `enable` / `disable`、`mwApi`、`userBlacklist`、`locales`、`permissions`、`github.webhooks`。
  - 重设：`assignee` 设为官方 bot（即激活这个群）、`guildId` 设为新群 openid、`flag` 设为 0、`createdAt` 设为迁移时间。
  - 新群已有记录时，复制清单内的字段覆盖，清单外的字段保留。
- `github.webhooks` 的订阅索引原本只在启动时重建：迁移后清除旧群（`onebot`）行上的订阅，并发出 `github/rebuild-index` 事件让 GitHub 插件重建索引，否则 `v5` 会一直往没有机器人的旧频道推送。
- 新旧两侧都只能迁移一次，记入审计表 `qqbot_migration`：旧群号、新群 openid、appid、操作者、时间。
- 官方 bot 无法核实旧群号与新群是不是同一个群，信任由 op 保证。

## 未决

- plugin-bind 读取 `tokenPrefix` 配置（默认 `koishi/`），但它的 Schema 没有声明这一项，传入后会不会被过滤，要实测。
- 群迁移是否加一道交叉证明：op 在旧群里通过 OneBot 发一次码，防止输错群号把私有仓库的 GitHub 推送串到别的群。
- 私聊菜单接口是否需要额外权限、写入后多久生效（文档未说明），要实测。
- 群提示第 1 步「点头像加好友」的实际操作路径，上线前在测试群里走一遍。
