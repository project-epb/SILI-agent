# OneBot → 官方 QQ bot 数据迁移设计

把 `v4`（OneBot）上的用户身份和群设置迁到 `v5`（官方 QQ bot）。官方 bot 的 openid 按「机器人 × 群 × 人」隔离，无法由 QQ 号推出，`union_openid` 也不可用，所以只能让用户自己证明「OneBot 上的这个账号和官方 bot 上的这个身份是同一个人」。

## 目标 / 非目标

- 目标：用户自助、一次性地把老账号绑到官方 bot 身份上；管理员按群一次性迁移群设置。
- 非目标：批量自动迁移；迁移期间继续提供 OneBot 上的任何其他服务；跨机器人的统一身份（`union_openid`）。

## 迁移期运行形态

- 新增 profile `v4-migrate`：只装 OneBot 适配器、Mongo 和迁移命令，**不提供任何其他服务**。
- `v5` 是独立进程，只连官方 bot，不加载 OneBot。
- 两个进程通过共用的 Mongo 交换迁移码和绑定结果。
- 迁移期结束后 `v4-migrate` 直接下线。

## 用户迁移

1. 用户**私聊官方 bot** 发迁移指令，bot 生成迁移码，只在这个私聊里回复。
2. 用户在 **OneBot 所在的群**里把迁移码发给 SILI（OneBot 是真实 QQ 号，不加好友，没有私聊，只能在群里提交）。
3. 校验通过后，把这个官方 openid 绑定到该 OneBot 账号对应的老 Koishi 用户上。

迁移码是一次性的、有短有效期，只在官方 bot 的私聊里显示。用户在群里发出的那一刻码即被**原子地消费并作废**，旁人看到时已无法使用，发出之前他们不可能知道这个码，所以公开提交是安全的。必须保证「校验 + 作废」是一个原子操作（例如 `findOneAndUpdate`），同一个码被两个人几乎同时提交时只有先到的一个成功。

绑定语义：

- 官方身份**覆盖绑定到老用户**，老用户的 `id`、`authority`、LLM 记忆（键是 Koishi `user.id`）等全部保留。
- 该官方身份此前如果已经自动生成了一个新的 Koishi 用户，其上的数据被老用户覆盖。
- 老账号（OneBot 绑定）标记为已迁移，**永久不再接受迁移**。
- 绑定数据里记录机器人的 appid，因为 openid 只在该机器人下有效。

## 群迁移

- 一个只有 `authority > 3` 才能用的命令，传入旧的 QQ 群号，确认后一次性迁移该群的频道设置。
- 迁移成功后旧群记录标记为已迁移，不能重复迁移。

## 未决

- 群迁移命令在哪里执行（官方 bot 所在的新群，参数填旧群号；还是在旧群里执行）。
- 迁移的频道字段范围（`switch` 的 enable/disable 列表、受理人等）。
- 迁移码的有效期和请求限频的具体数值。
- v5 关闭 `autoAssign` 后，群迁移命令是否同时负责给新群分配受理人。
