# OneBot → 官方 QQ bot 数据迁移设计

把 `v4`（OneBot）上的用户身份和群设置迁到 `v5`（官方 QQ bot）。官方 bot 的 openid 按「机器人 × 人」区分（同一机器人下，同一个人在各群和私聊里的 openid 相同），无法由 QQ 号推出，`union_openid` 也不可用，所以由用户自己证明「OneBot 上的这个 QQ 号和官方 bot 上的这个身份是同一个人」。

## 目标 / 非目标

- 目标：用户自助把老账号绑到官方 bot 身份上；op 按群一次性迁移群设置。
- 非目标：批量自动迁移；迁移期间继续提供 OneBot 上的任何其他服务；跨机器人的统一身份（`union_openid`）。

## 迁移期运行形态

- 新增 profile `v4-migrate`：只装 Mongo、OneBot 适配器、迁移码提交处理和进程级错误监听，**不装 `FallbackHandler` 等任何其他插件，不提供其他服务**。
- `v5` 是独立进程，只连官方 bot，不加载 OneBot。两个进程通过共用的 Mongo 交换迁移数据。
- 依赖顺序：用户迁移要求普通用户能私聊官方 bot，即机器人已在后台公开；公开之前，访问控制 spec 里的守卫必须完成并验证。
- 迁移期结束后 `v4-migrate` 下线。

## 用户迁移

1. 用户私聊官方 bot：`迁移 <旧 QQ 号>`。bot 生成迁移码，与（appid、openid、旧 QQ 号）绑定，只在这个私聊里回复。迁移命令是私聊守卫的例外，陌生人也能用。
2. 用户在任意有 OneBot SILI 的群里发出迁移码。OneBot 是真实 QQ 号，不加好友，没有私聊，只能在群里提交。`v4-migrate` 只处理以迁移码固定前缀开头的消息，不需要 @。**发送者的 QQ 号必须等于迁移码绑定的旧 QQ 号。**
3. 校验通过后完成改绑。

迁移码：

- 固定前缀加至少 8 位 base32，有效期 10 分钟，一次性。
- 每个 openid 同时只有一个有效码；按 openid 限制领码频率，按 QQ 号限制提交失败次数。
- 旁人看到群里的码也用不了：码一经提交即被消费作废，而且发送者必须是绑定的那个 QQ 号。

群里的回复只说结果，不带 openid、权限等信息。提交前的提示文案写明：「这会把你的账号交给领取这个迁移码的那个身份，不是你本人领取的请不要发送」。

改绑语义：

- 写入 `binding`（`platform = qq`，`pid = openid`），`aid = bid = 老用户 id`。老用户的 `id`、`authority`、LLM 记忆全部保留（记忆键是 Koishi `user.id`；平台名里 OneBot 映射为 `qq`，与官方适配器一致，迁移后能直接接上）。
- 这个 openid 此前如果已经自动生成过一个新用户，该用户变成孤儿：它的 LLM 对话、会话和记忆，GitHub token，rate-limit 计数，callme 称呼都不再可达。被替换的新用户 id 写进迁移审计表，便于人工恢复。
- 改绑时这个 openid 如果有正在处理的会话，之后的写入可能落到老用户上（Koishi 按写入时的 binding 落库），影响限于少量字段，接受。
- `v5` 不装 `@koishijs/plugin-bind`，否则 `bind -r` 能撤销迁移写入的绑定。

一致性（生产 Mongo 是单机部署，没有事务）：

- 真正的闸门是对迁移状态行的条件更新（minato 的 `set` 返回 `modified`），保证同一个旧 QQ 号同一时刻只有一个迁移在进行。
- 步骤依次为：条件消费迁移码 → 条件锁定旧账号的迁移状态 → 写 `binding` → 写审计并标记完成。每一步都可以重放，中途崩溃时按迁移状态行和审计记录续做。

## 群迁移

- 在官方 bot 所在的新群里 `@bot` 执行，要求 `authority ≥ 4`，参数是旧的真实 QQ 群号。op 在私聊完成用户迁移后，在群里是同一个身份。这条命令是群守卫的白名单命令，可以在未激活的群里执行。
- 两段式，不用 `session.prompt`（未激活的群里，非白名单消息会被守卫丢弃）：不带 `-y` 时只展示预览，包括新群名称（官方 `info` 接口）和旧群记录摘要；带 `-y` 才执行。
- 字段处理：
  - 复制：`switch` 的 `enable` / `disable`、`mwApi`、`userBlacklist`、`locales`、`permissions`、`github.webhooks`。
  - 重设：`assignee` 设为官方 bot（即激活这个群）、`guildId` 设为新群 openid、`flag` 设为 0、`createdAt` 设为迁移时间。
  - 新群已有记录时，复制清单内的字段覆盖，清单外的字段保留。
- `github.webhooks` 的订阅索引只在启动时重建：迁移后要触发重建，并清除旧群（`onebot`）行上的订阅，否则 `v5` 会一直往没有机器人的旧频道推送。
- 新旧两侧都只能迁移一次，记入迁移审计。
- 官方 bot 无法核实旧群号与新群是不是同一个群，信任由 op 保证。

## 迁移审计表 `qqbot_migration`

用户迁移与群迁移共用：类型、旧标识（QQ 号或群号）、新标识（openid 或群 openid）、appid、状态、被替换的新用户 id、操作者、时间。

## 未决

- **老账号迁移后能否再次迁移。** 建议允许本人重迁，以最后一次为准：钓鱼得手（诱骗受害者发出攻击者领取的迁移码）时，受害者能用自己的官方身份重新迁回；如果永久锁定，钓鱼一次就永久失去账号。这与先前「迁移后不再接受迁移」的结论相反，待确认。
- 领码限频、提交失败限次的具体数值。
- 群迁移是否加一道交叉证明：op 在旧群里通过 `v4-migrate` 发一次码，防止输错群号把私有仓库的 GitHub 推送串到别的群。
