# OneBot → 官方 QQ bot 数据迁移设计

把 `v4`（OneBot）上的用户身份和群设置迁到 `v5`（官方 QQ bot）。在 Koishi 里 OneBot 和官方 QQ bot 是两个不同的平台，大多数用户数据在 OneBot 这边。官方 bot 的 openid 按「机器人 × 人」区分（同一机器人下，同一个人在各群和私聊里的 openid 相同），无法由 QQ 号推出，`union_openid` 也不可用，所以由用户自己证明「OneBot 上的这个 QQ 号和官方 bot 上的这个身份是同一个人」。

## 目标 / 非目标

- 目标：用户自助把官方 bot 上的身份并入 OneBot 上的老账号；op 按群一次性迁移群设置。
- 非目标：批量自动迁移；迁移期间继续提供 OneBot 上的任何其他服务；跨机器人的统一身份（`union_openid`）。

## 迁移期运行形态

- 同一时间只运行 `v5` 一个进程。迁移期间 `v5` 额外加载 OneBot 适配器（以 `ONEBOT_SELFID` 是否设置为开关），**OneBot 只接收绑定码，其余一概不处理**：所有 OneBot 会话被访问控制的守卫视为未服务，不建用户、不建频道、不入库（见访问控制 spec「迁移期的 OneBot 会话」）。
- 依赖顺序：用户迁移要求普通用户能私聊官方 bot，即机器人已在后台公开；公开之前，访问控制 spec 里的守卫必须完成并验证。
- 迁移期结束后删除 `ONEBOT_SELFID`，OneBot 不再加载，不需要改代码。

## 用户迁移：使用 `@koishijs/plugin-bind`

用户迁移不另写代码，直接用 Koishi 的 `bind` 命令。它本来就是 SILI 跨平台（Discord、钉钉等）合并账号的工具，迁移只是其中一种用法。

流程：

1. 用户私聊官方 SILI 发 `bind`，得到绑定码（5 分钟有效，存在内存里，重启即失效）。
2. 用户用旧 QQ 号，在任意一个有旧 SILI 的群里把绑定码原样发出。OneBot 是真实 QQ 号，不加好友，没有私聊，只能在群里发。
3. 官方 bot 上的身份并入旧账号。

`bind` 的语义（`@koishijs/plugin-bind` 1.5.1）：

- 发起 `bind` 的账号，并入**发出绑定码**的账号所属的 Koishi 用户：把 `binding`（`platform = qq`，`pid = openid`）的 `aid` 改为旧用户 id，`bid` 保留发起方原来的用户 id。数据不合并，只是换了归属。
- 旧用户的 `id`、`authority`、LLM 记忆全部保留（记忆键是 Koishi `user.id`；记忆的平台名里 OneBot 映射为 `qq`，与官方适配器一致，并入后能直接接上）。
- 发起方原来的用户不再使用。它通常是空的：私聊守卫只在用户发 `bind` 时才为他建用户。迁移前已经在已激活的群里用过新机器人的用户，那部分数据会随之不再可达；在迁移公告里提醒「先迁移再使用」。
- 用户可以在官方 bot 上发 `bind -r` 撤销，身份退回到 `bid` 指向的原用户，旧账号不受影响。
- 一个旧账号可以被多个身份并入（共用同一份数据），不存在「迁移后锁定」。
- 改绑时如果这个 openid 有正在处理的会话，之后的写入可能落到旧用户上（Koishi 按写入时的 binding 落库），影响限于少量字段，接受。

`bind` 的最后一步用 minato 的 `set` 改写发起方的绑定行，而 `set` 只更新已有的行、不会新建。所以发起方必须已经有用户和绑定记录：私聊守卫对 `bind` 放行时，`autoAuthorize` 必须返回 1（见访问控制 spec）。否则插件会回复「绑定成功」，实际什么都没写。

文案：plugin-bind 自带的 zh-CN 文案（「原始平台 / 目标平台」）很难读，在 `v5` 里覆盖。Koishi 的 i18n 后定义的生效，所以覆盖必须在 plugin-bind 加载之后（它注入 `database`，覆盖的插件也要等 `database` 就绪并排在它后面）。文案要通用，因为 `bind` 也用于绑定 Discord、钉钉等平台：

```yaml
commands.bind:
  description: 绑定其他平台的账号
  messages:
    generated-1: |-
      绑定码：{0}
      请在 5 分钟内，用你想保留数据的那个账号（比如旧 QQ 号、Discord、钉钉）把这行发给 SILI。
      完成后，当前账号会并入那个账号，两边共用同一份数据（权限、记忆、称呼），当前账号原有的数据不再使用。
      想撤销的话，随时在当前账号发「bind -r」。
    generated-2: |-
      第一步完成。请在 5 分钟内，用最开始发起绑定的那个账号把下面这行发给 SILI：
      {0}
      完成后，那个账号会并入当前账号，当前账号的数据保留。
    self-1: 这串码要用另一个账号发，也就是你想保留数据的那个。
    self-2: 这串码要用最开始发起绑定的那个账号发。
    success: 绑定成功，两个账号现在共用同一份数据。
    remove-success: 已解除绑定，当前账号恢复为独立账号。
    remove-original: 无法解除：这是你的原始账号。
```

迁移的具体说法（「私聊新 SILI 发 `bind`，再用旧 QQ 号在群里发出绑定码」）写进迁移公告，不写进命令文案。

风险：钓鱼。攻击者把自己领的绑定码诱骗别人在群里发出，攻击者的身份就并入了受害者的账号。命令文案防不住（文案只给领码的人看），在迁移公告和群公告里写明「绑定码只能是你自己领的，别人给你的码不要发」。受害者事后没法把攻击者踢出去，需要管理员处理。

## 群迁移

- 在官方 bot 所在的新群里 `@bot` 执行，要求 `authority ≥ 4`，参数是旧的真实 QQ 群号。op 在私聊完成用户迁移后，在群里是同一个身份。这条命令是群守卫的白名单命令，可以在未激活的群里执行。
- 两段式，不用 `session.prompt`（未激活的群里，非白名单消息会被守卫丢弃）：不带 `-y` 时只展示预览，包括新群名称（官方 `info` 接口）和旧群记录摘要；带 `-y` 才执行。
- 字段处理：
  - 复制：`switch` 的 `enable` / `disable`、`mwApi`、`userBlacklist`、`locales`、`permissions`、`github.webhooks`。
  - 重设：`assignee` 设为官方 bot（即激活这个群）、`guildId` 设为新群 openid、`flag` 设为 0、`createdAt` 设为迁移时间。
  - 新群已有记录时，复制清单内的字段覆盖，清单外的字段保留。
- `github.webhooks` 的订阅索引只在启动时重建：迁移后要触发重建，并清除旧群（`onebot`）行上的订阅，否则 `v5` 会一直往没有机器人的旧频道推送。
- 新旧两侧都只能迁移一次，记入审计表 `qqbot_migration`：旧群号、新群 openid、appid、操作者、时间。
- 官方 bot 无法核实旧群号与新群是不是同一个群，信任由 op 保证。

## 未决

- plugin-bind 读取 `tokenPrefix` 配置（默认 `koishi/`），但它的 Schema 没有声明这一项，传入后会不会被过滤，要实测。
- 群迁移是否加一道交叉证明：op 在旧群里通过 OneBot 发一次码，防止输错群号把私有仓库的 GitHub 推送串到别的群。
