# 没有正常结束的轮次

## Goal

LLM 的一轮对话出错（DeepSeek DSML leak、网络错误）或进程中途退出时，这一轮从历史里整个消失：用户消息要等轮次正常结束才入库，加载历史时又丢弃不完整的轮次。模型下一轮看不到用户要了什么、自己已经执行过哪些工具，可能重复执行不幂等的操作（例如再次 `feature -e`）。参照 Claude Code 和 only-chat，让这样的轮次保留下来，并告诉模型它被中断了。

## Scope

- In：聊天轮次的入库时机与状态；加载历史时修复不完整的轮次；下一条用户消息的中断提示。
- Out：DM 里用户打断的现有机制（pre-stream 拼接上一句、mid-stream 的 `<interrupt_notice>`）照旧；报错时发到群里的文案照旧。

## Decisions

1. **用户消息在轮次开始时入库，带状态 `turn_status`：`running` → `done` / `aborted` / `failed`。** 失败原因写在 `turn_error`，只给人看。没有状态的旧数据视为 `done`。
   Why：出错路径不一定跑得到（进程被杀、重启），只有一开始就落库才不丢；进程退出后留下的 `running` 就是被中断的轮次。

2. **工具调用边执行边入库。** 带 tool_calls 的助手消息在执行工具前入库，每个工具结果一出来就入库；用户打断时已经完成的工具结果照样保留。steer 进来的消息仍附在最后一个工具结果后面，追加时更新那一行。
   Why：执行过的工具产生了副作用，历史必须如实反映，模型才不会重复执行。

3. **修复发生在加载历史时，不写入数据库。** 加载历史的纯函数对状态不是 `done` 的轮次：
   - 保留用户消息、已入库的助手消息和工具结果；
   - 没有结果的工具调用当场补一条占位结果；
   - 没有对应调用的工具结果丢弃；
   - 允许没有最终回复。
   状态为 `done` 却不完整的轮次照旧丢弃。
   Why：读时修复对任何中断原因都成立；占位不入库，迟到的真实结果入库后自然取代它（only-chat 的做法）。

4. **中断后的下一条用户消息开头加一行提示，提示也是加载时推出来的，不入库。** 当前这条用户消息同理：上一轮被中断时，发出去的内容开头加同样的提示，入库的内容不带。
   - `aborted`：`[Request interrupted by user]`，工具占位 `[Request interrupted by user for tool use]`（Claude Code 原文）。
   - `failed` 和遗留的 `running`：`[Request interrupted by an error]`，工具占位 `[Request interrupted by an error during tool use]`。
   Why：提示按同一规则推出，重放时与当初发送的字节一致，不破坏 prompt cache。用模型熟悉的短句，不解释、不写具体原因（only-chat 实测长说明反而让模型困惑）；但如实区分「用户打断」和「出错」。
   Rejected：工具占位写成 error——模型会认为工具不可靠、以后不敢用（only-chat 的结论）。

5. **什么都没留下的轮次：** 用户打断且除用户消息外没有任何记录时，删掉这条用户消息（新一轮的 pre-stream 拼接已经带上了它）；SILI 选择沉默时，删掉这一轮的全部记录（与原来一样不入库）。出错且什么都没留下的轮次保留，后面紧跟下一条用户消息。
   Why：DeepSeek 实测接受「工具结果后直接跟用户消息」和「两条用户消息相连」，无需合并。

## Acceptance

- 一轮在执行过工具后因 DSML leak 失败：下一轮的请求里能看到这一轮的用户消息、工具调用与结果，下一条用户消息以 `[Request interrupted by an error]` 开头。
- 工具执行中途进程重启：重启后的下一轮请求合法，缺失的工具结果有占位。
- 群里两轮之间的 steer、DM 打断、SILI 沉默的表现与之前相同。
- 连续两轮请求里，上一轮发送的用户消息与下一轮重放的字节一致。
