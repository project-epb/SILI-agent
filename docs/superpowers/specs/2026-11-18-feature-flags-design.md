# 服务等级（feature）

## Goal

v5 里「某个功能在哪能用」由四套互相打补丁的机制决定：koishi-plugin-switch 的按群开关、给它补漏的 `SilentSwitch`、qqbot 门控里写死的免激活白名单（还要和 profile 里的 `PluginCollectionPublic` 手动同步）、ComfyUI 自带的频道白名单。新增一个要小范围开放的功能（ComfyUI）就得改 env 再重启。用一个自己的 `feature` 插件取代它们：仿照 Koishi 的用户权限等级，给群和指令各定一个服务等级。

## Scope

- In：`feature` 插件与指令；指令和群的服务等级；按群覆写；群激活的入口并入 `feature`；控制台按群开关功能；门控的放行名单改由等级推出；ComfyUI、NovelAI 设为高等级；删掉 `channel.activate`；v5 不再加载 koishi-plugin-switch、`SilentSwitch`，不再给 ComfyUI 传 `allowedChannels`、不再给 NovelAI 传频道（这些 v4 仍在用，代码保留）。
- Out：激活的存储和连带逻辑（`qqbot_channel.activated`、served 上下文、首次激活通知、群迁移、被移出群取消激活）照旧；私聊激活（`qqbot_user.dmActive`、`user.activate`、控制台私聊开关）照旧；v4 profile 保持原样；在控制台修改指令等级；按群过滤 LLM 的指令目录。

## Decisions

1. **指令有服务等级，默认 1；群有服务等级，指令等级不高于群等级就能用。**
   - 指令等级 0：任何群和私聊都能直接用（试用）。
   - 指令等级 1（不声明）：激活后可用。
   - 高等级（ComfyUI、NovelAI 用 100）：没有群会自动达到，只能按群覆写打开。
   Why：沿用 Koishi 权限等级的思路，一个数字比较就够；以后要加中间档只需多一个数。

2. **群等级就是激活状态：未激活 0，已激活 1。** 私聊同理（op 和激活过的私聊为 1）。非 QQ 官方平台一律视为 1。不新增存储。
   Why：现在只需要两档；真要用到 2 级时再把激活改存数字。

3. **指令等级跟着指令声明。** 自己的插件在 `ctx.command` 的配置里写 `featLevel`（如 `ctx.command('foo', '', { featLevel: 100 })`）；第三方插件的指令由 profile 在 `feature` 插件的 `featLevels` 配置里按指令名列出等级。子指令继承最近一层声明的等级。
   Why：等级写在功能旁边，不再有两处要手动同步的名单。

4. **按群覆写优先级最高。** 每个群或私聊有一份覆写 `Record<指令名, boolean>`，可以把某个指令强制打开（true）或强制关闭（false），判定沿父指令链向上：链上任一层被强制关闭就关；否则链上任一层被强制打开就开；否则比较等级。修改时若结果与本群按等级的默认状态相同，就删掉这条记录（例：`-d callme` 记下 `{ callme: false }`，之后 `-e callme` 记录清空；op 给 1 级群 `-e comfyui` 记下 `{ comfyui: true }`，之后群管理 `-d comfyui` 记录清空）。
   Why：灰度功能逐群开放，日常功能也能逐群关掉。

5. **覆写存在 `feature` 自己的表里**，按（平台，频道）记一份覆写，私聊的频道记为 `private:<用户 id>`。启动时整表载入内存，写入时同步更新。上线时把 v5 各群现有的 `channel.disable` 手动迁移一次，不写进代码。
   Why：Koishi 处理私聊时不加载频道行，沿用 `channel.enable/disable` 存不了私聊；门控是同步路径，判定必须读内存。
   Rejected：存在 `channel` 表上（`channel.feat_override`）或沿用 switch 的 `channel.enable/disable`——私聊存不下。

6. **指令是 `feature`，别名 `feat`、「功能」。**
   - `feature`：第一行是本群等级（试用 / 已激活），之后列出强制打开和关闭的功能。
   - `feature -e <指令...>` / `feature -d <指令...>`：强制打开 / 关闭；`-r <指令...>` 恢复默认。
   - `feature -a`：激活本群；`feature -a -r`：取消激活。调用 qqbot 现有的激活逻辑，取代 `channel.activate`（含别名「激活」），门控在未激活群里给 op 放行它。私聊里不可用，私聊激活仍用 `user.activate`。
   - 一个功能能用要同时满足：群等级 ≥ 指令等级（或被覆写打开），且用户权限 ≥ 指令权限（Koishi 原有检查）。
   - 权限 3（群管理、维护员）：可以关闭和恢复任何功能，但不能打开等级高于本群等级的功能。权限 4（op）：任意覆写，以及激活与取消激活。都只能操作权限不高于自己的指令。
   Why：激活就是群等级，与功能开关放在同一个入口；花钱的功能只有 op 能放。

7. **覆写打开只在消息能到达插件的群里生效。** 未激活群的消息在进入 Koishi 前由门控丢弃（只放行等级 0 的指令），等级 1 以上的插件也只装在服务已激活会话的上下文里；所以在未激活群里强制打开等级 1 以上的指令不会生效，`feature -e` 在这种情况下拒绝并提示先激活。
   Why：门控在建用户、建频道行之前丢消息，防陌生群撑满数据库，要保留。

8. **没开的功能：人直接调用时静默，SILI 调用时说明原因。** 判定挂在指令执行前的检查上，所有调用路径（消息解析、shortcut、兜底转 chat、LLM 工具）都经过它。默认返回空、什么都不发；LLM 工具调用时（调用参数上带 agent 标记）返回一句给模型看的说明（本群没开放、不要重试）。
   Why：静默能避免在关掉功能的群里刷屏；但 LLM 拿到空结果会编造「画好了」，必须告诉它。

9. **LLM 的指令目录不按群过滤。**
   Why：目录在 system prompt 里，所有群和后台任务（空闲压缩、记忆 fork）共用一份以命中 prompt cache；按群过滤会让缓存失效，省下的只是几行目录。没开的功能由第 8 条兜住。

10. **门控的免激活放行名单由等级推出。** 未激活的群和私聊里，等级 0 的指令（含别名、子指令）放行，其余照旧丢弃；被本群关掉的等级 0 指令由第 8 条静默。op 专用的 `feature`、群迁移、私聊的 `bind` 仍由门控单独放行。`[[词条]]` 链接照旧放行。私聊里用不了的指令（`wiki`、`github`）由各自的插件处理，不再单独维护私聊名单。

11. **等级 0 指令所在的插件仍须装在 profile 的 public 上下文里。** `feature` 启动后检查：等级 0 的指令若注册在只服务已激活会话的上下文里，记一条错误日志。
    Why：插件装在哪个上下文决定它能不能收到未激活会话，`feature` 只能判定、不能替它收消息。

12. **控制台按群开关功能。** 频道管理器（`qqbot-admin`）每个群和私聊行有「功能」面板（激活开关仍在行上）：面板顶部显示群等级，下面列出全部顶层指令及其等级、当前是否可用、是否被覆写，可强制打开 / 关闭 / 恢复默认。等级只读，只在代码里声明。`feature` 服务提供「列出频道的功能状态」和「修改覆写」两个方法，指令和控制台都调它们。

13. **ComfyUI 和 NovelAI 等级 100。** 上线后在小鱼君测试沙盒、艾尔奇亚联邦国立金属研究所（NGNL 闲聊群）和小鱼君的私聊里打开 ComfyUI。

## Acceptance

- 未激活群：`help`、`dice`、`wiki` 能用；聊天、pixiv 没反应；`[[词条]]` 照常展开。
- op 在未激活群里 `feature -a` 后等级 1 的功能可用，`feature -a -r` 后回到只有等级 0；`channel.activate` 不再存在。
- 已激活群：`comfyui.generate` 没反应，让 SILI 画图时它说本群没开放画图。
- op 在群里 `feature -e comfyui` 后可以画图；`feature -r comfyui` 后恢复关闭。权限 3 的用户执行 `feature -e comfyui` 被拒绝，执行 `feature -d chat` 成功。
- `feature -d chat` 后该群和 SILI 聊天没反应；之前用 switch 关掉的功能上线后仍然是关的。
- 小鱼君私聊 `feature -e comfyui` 后可以画图，别人的私聊不行。
- 控制台打开某群的「功能」面板能看到激活状态和每个功能的状态，在面板里开关的效果与指令相同。
- v5 不再加载 koishi-plugin-switch 和 `SilentSwitch`，qqbot 里没有写死的免激活名单，v5 不再传 ComfyUI、NovelAI 的频道白名单。
